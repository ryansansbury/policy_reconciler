# Design questions

These are the questions an engineer is most likely to ask about Policy Reconciler, and each answer comes from the code and names the file to open.

## The ideas behind it

- **Certainty and the AI queue.** Code decides only when one reading is possible, and everything else is queued. The queue holds about 150 clauses out of about 1,500 per library.
- **AI proposes and code verifies.** Every AI answer is checked by code before anything uses it, and an answer that fails twice is held with its reasons instead of shown.
- **Values only through citations.** A consolidated draft can't introduce a number. Every value in it is a placeholder that code fills from a clause, and the gate fails anything else.
- **Record and replay.** The page never calls a model. Each AI step was recorded once, and the build replays the recordings and checks them again on every build.
- **Deliberate variation.** A Colorado addendum that sets a 45-day notice against a bank-wide rule of 30 days isn't a conflict because it narrows the scope on purpose. Code tells the difference by comparing scopes and not values.
- **Authority.** The stronger document wins when two statements of one rule disagree. The finding names the authority so the fix is clear. The scorer checks that authority too, and on the development seeds it was right for 98 of 99 contradictions. The one miss was a policy statement code couldn't read, and the rule extractor exists for clauses like that one.
- **Freezing and held-out scoring.** The answer key's first version froze before any detector existed, its one fix came from the development seeds before any held-out seed was scored, and the engine froze before its one scoring on seeds it had never seen. That's what keeps a score from being tuned to the answers.
- **Why the code score is optimistic.** Held-out seeds use the same phrasing families as the development seeds so they test new documents and values but not new writing. Forty clauses written by hand in wording the generator never uses test that, and on them code alone read 6 of the 36 rules while the extractor read 34 exactly, held the other 2 for a failed check, and invented none.

## Thirty questions

1. **What happens when someone clicks "Run the review"?** The page replays a run the build already made. `engine/pipeline.py` parsed every file, extracted what code could read, compared every statement of every rule, and found duplicates and older versions, and `agents/flow.py` replayed the AI steps' recordings into that review before the page was written.
2. **How does a clause get its ID?** `engine/parse.py` names each clause by its position as document, version, section, and clause so the same clause always gets the same ID and every finding can point at exact words in an exact file.
3. **When is code certain about a clause?** `engine/extract.py` calls a clause certain only when exactly one tracked rule's cue words match with exactly one value of the right type and the actor the rule belongs to. Anything else goes to the AI queue with its reason, and code never guesses.
4. **Why does a count need something counted after it?** Without that rule "for one account" read as a count of one and invented a rule. `engine/values.py` now needs a counted plural or "per" after the number.
5. **How does code know who a rule applies to?** `engine/scope.py` starts from the document's "Applies to" line and narrows it with the clause's own words such as "In Colorado branches" or "For commercial accounts."
6. **What makes a difference deliberate?** `scope.deliberate` treats a difference as intended when the scopes don't overlap or when one side narrows the scope on purpose in its own words or as a state addendum. Those differences are recorded as variations with their reasons and never flagged.
7. **How is the authority chosen?** `compare.standing` ranks a state addendum first for its state, then a policy, a procedure, and then a job aid, FAQ, or bulletin, and the newer one wins a tie. The finding names the authority so the fix is clear.
8. **Why compare only current versions?** An older version still in the library isn't a contradiction with its own replacement. `compare.superseded` reports it once as an outdated version with the values that changed.
9. **How do duplicates work?** `engine/duplicates.py` looks for runs of at least three consecutive matching clauses in two documents of the same topic. Single matching steps were too common to mean anything because procedures share standard steps.
10. **How do you keep the scores honest?** The answer key's first version froze before any detector existed, its one fix landed before any held-out scoring, and `evals/frozen.json` and `evals/engine_freeze.json` hold the hashes that tests check. A held-out library is scored once for each frozen version, and a new version gets seeds no earlier version saw.
11. **What does the rule extractor see?** `agents/inputs.py` gives it the queued clause with its heading and its document's title, type, and "Applies to" line, and `prompts/extract.md` asks for atoms in the same shape code produces. It never sees the answer key.
12. **How do you check what it returns?** `agents/validate.py` needs every value quoted word for word from the clause, and code reads the quote back to check it holds the same value. Roles come from a fixed list, and the vocabulary in the prompt comes from the same code the validator uses.
13. **What happens when a reply fails?** The recording run sent one repair request listing the problems for just the failed items, and items whose repair failed too were held with their reasons. The page shows them as held. This repo only replays, and the recorder itself isn't part of it.
14. **What's the cache key?** Each recording carries the step, the prompt's hash, the model, and a hash of the masked input. `agents/replay.py` uses an answer only when the model saw exactly what code would send today, and that means a regenerated library never reuses an old answer.
15. **How do you know nothing sensitive left the machine?** `agents/mask.py` replaces account numbers, ID numbers, phone numbers, email addresses, and customer names before every call, and each recording holds only the masked text that was sent.
16. **When does a pair go to the classifier?** `agents/combine.py` holds back a comparison when the deadlines share a number but not a unit, when one side names a general role, when one side carries a condition, or when the AI inferred an actor. Every other comparison code settles itself.
17. **Why does only "conflict" become a finding?** The classifier's other labels explain why a pair wasn't flagged, and keeping them as explanations means a model can never add a finding by saying something softer.
18. **How do the experts' decisions change what code does?** `agents/decisions.py` turns each decision into a rule, and `combine.review` applies it to every pair of that group instead of asking the classifier. A test in `tests/test_decisions.py` holds code to each one.
19. **Why Cohen's kappa?** Raw agreement looks high when one label is common, and kappa in `evals/agreement.py` corrects for the agreement chance alone would produce.
20. **How does the gate work?** The drafter writes every value as a placeholder that names its clause, and `engine/gate.py` fails any draft that uses a placeholder it wasn't given, cites nothing, or shows a value outside a placeholder. A draft that passes is filled in with each clause's own words.
21. **Why do modal words and roles count as values?** That word is the rule when a rule's value is "must" or a role. The gate treats it like a number for those rules so a draft can't change who approves or whether something is required.
22. **How is the judge calibrated?** `agents/judging.py` compares the judge's grades with the experts' shared grades on drafts with known defects. The judge is trusted only on criteria where it agrees nine times in ten, and a person checks every other criterion.
23. **Why can't the judge come from the drafter's family?** A model can favor writing that reads like its own. `agents/routing.py` never picks that pairing, and no recorded judgment in this repo has one.
24. **How does keyword search rank clauses?** `engine/search.py` uses BM25 to give more weight to a question's rarer words, add less for each repeat of a word, and discount long clauses.
25. **What does the assistant's check enforce?** `agents/assisting.py` fails an answer that cites a clause it wasn't given or states a value no cited clause holds. When the cited clauses disagree the answer has to say so.
26. **How does routing choose a model?** `agents/routing.py` takes the cheapest model that clears the step's bar within the client's approved vendors and gives a tie to the faster one. The other models that clear the bar become the fallbacks.
27. **How does an incremental run work?** `engine/incremental.py` hashes every section, and a change rereads only the sections whose hashes changed and compares only the rules those sections state. Everything else is reused.
28. **What does the CI gate check?** `ci/run_gate.py` runs every test, the build with its strip check, a scan for commas before "so," a scan for anything shaped like an API key, and the regression thresholds in `config/gate.json`.
29. **How do you keep a client's name off a page like this?** `app/never.py` scans the whole page and its data for every never-word, and `app/bundle.py` stops the build when one appears. A private build supplies its own list, this public copy ships none, and a test plants a word to prove the scan still fails a build.
30. **What would break first at a real bank?** Scanned PDFs, wording the vocabulary has never seen, and problems that only appear when several clauses are read together. The first two land in the AI queue instead of disappearing, and the third is listed as out of scope.

## What failed, and how it was fixed

- The first catalog let a business-line variation land where a document scoped to just that line already stated the bank-wide value. That's a real conflict, and the development seeds caught it. Catalog version 2 fixed it before any held-out seed was scored.
- A modal reader that assumed "must" by default turned ordinary steps into rules. It now needs real modal language.
- A count reader picked up "one" from "for one account" and invented a rule. A count now needs something counted after it.
- Quick-reference table rows use labels instead of sentences so their cue words needed the labels' synonyms.
- A state addendum applies to every business line, and that made it look broader than a consumer rule and hid a real conflict. Narrowing on either states or lines now counts as deliberate.
- Standard steps shared by procedures looked like copies. A duplicate now needs three consecutive matching clauses.
- The first held-out run of the AI steps found three findings where two statements carried the same exception and were paired as if one had left it out. That's fixed, and the fixed version was scored again on libraries no version had seen.
- On the second run an AI reading with an exception became a rule's authority and turned a contradiction code had already found into a doubtful pair. The classifier then let it go. Now a statement that contradicts a certain statement stays a certain finding.
- The classifier labeled two statements of the same rule "duplicate" when they were simply consistent. The prompt now defines a duplicate as a copied run of steps. A single pair of identical clauses can't show a copied run, and its decision accuracy counts duplicate and consistent as one outcome.
- Routing first took the gate as the drafter's whole bar, and it chose GPT-6 Luna. Reading the drafts side by side showed that Luna and Claude Haiku had dropped "the same day" from a rule. The judge now reads every model's comparison drafts before a drafter can route.
- The comparison first priced Claude by what its recordings reported, and that roughly doubled its cost against the other vendors. A line through five steps whose messages differ in size showed a fixed 4,900 tokens of client context per call, and Claude is now priced without it.
- The judge failed drafts that added Staff as the subject because its prompt counts any role the sources don't name as a new rule. The drafter's own prompt shows that subject in its examples. The specialist ruled it harmless, and the next prompt version should make the two prompts agree.
- The model comparison measured extraction on every third clause, and GPT-6 Luna read all 60 exactly. On the demo's full queue it read a branch manager limit into the personal banker clause and an approver into the two-forms-of-ID clause, and the drafts built on those readings would have changed two rules. It also read a procedure's subject as a condition, and the draft built on that reading names management where the policy names the regional manager. The judge passed all three because it grades a draft against the clause it keeps, and the specialist caught them at approval. Extraction is now measured on all 180 clauses, and there Luna misses the bar on its own.
- The combined review replayed the classifier with the extractor's model, and a classifier on another model was ignored. Each step now replays its own model, and the comparison builds its items on the configured models so turning routes on never changes what it measured.
- The extraction bar of one point turned out smaller than one model's own difference between two runs of the same clauses. Sonnet read 180 of 180 exactly in its scored run and 178 in the comparison. A route between close models needs repeated runs or a person's hold.
